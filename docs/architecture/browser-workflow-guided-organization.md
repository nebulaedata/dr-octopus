## 1. 目的与边界

整理的目的是将一次录制转为可复用流程：保留事实顺序、说明操作意图、提取下次运行所需参数，在不确定处请用户决策。整理不执行页面动作，不证明业务完成，也不把模型文字当成录制证据。

现有实现依据：workflow-compiler.ts一次请求生成语义，workflow-assembly.ts组装程序拥有的动作；workflow-messages.ts任务只有starting/running及终态，没有待回答契约；workflow-service.ts在Worker重启时中断在途任务。workflow-quality.ts明确没有采集业务完成结果，当前Schema却要求至少一个成功条件；WorkflowReview只能直接修改条件expected。它们是本提案需要改变的实际落点，不假定现有代码已支持多轮问答。

用户于2026-10-31确认继续先设计。此前第二阶段人工验收通过，不等于本提案实施或测试完成；实施前必须重新读取用户近期改动。保留其“步骤详情核对与执行确认同行、发布后返回列表”的现有行为。

本期不做：自由聊天、任意工具调用、追加网页采集、自动重放、Skills生成/导出、通用Agent框架或全局状态库。复用现有AI SDK调用、扩展Agent Host和Worker；不修改packages/agent、Executor或共享shadcn组件。

## 2. 用户流程

1. 点击“整理为工作流”：沿用模型配置与发送授权检查，开始分析已有脱敏记录。
2. 信息充分：直接生成草稿预览，不为了展示智能体而硬塞问题。
3. 有关键不确定性：进入“需要你确认”，每次只展示一个问题、关联步骤和2～4个有效选项，另有固定“暂不确定”。
4. 用户选择后点击“确认并继续”：先持久化答案，再切到下一个已生成问题；不能点击选项就收费调用。批次全部回答后，确有需要才进行下一轮分析。
5. 最终生成可审阅草稿：概括步骤、参数、用户明确的目标及仍未解决的问题。最终保存/发布由用户明确触发，不自动发布。

没有常驻输入框、消息发送栏、聊天头像或漫长对话记录。“补充说明”是当前问题的可选短文本，最多300字；不能脱离当前问题开启任务。禁止询问密钥、密码、验证码或具体订单号等本次运行值；这里只讨论参数含义和流程目标。可选说明提交前可见将用于整理，敏感内容不得因简单过滤就承诺必然安全。

## 3. 只问影响结果的问题

| 类别     | 合理问题                                     | 不应提问或推断                         |
| -------- | -------------------------------------------- | -------------------------------------- |
| 操作意图 | “这里的无标题按钮用于什么？”并附该步骤证据   | 对清楚的“查询”反复确认                 |
| 参数含义 | “这两个编号分别用于哪一步？”                 | 要求用户填写真实编号、生成未录制默认值 |
| 完成目标 | “这个流程做到哪里就算完成？”                 | 把“按钮可见”自动说成“订单已提交”       |
| 证据缺口 | “这一步无法从记录确定，是否先保留为待核对？” | 猜测丢失的点击或凭回答发明操作         |

程序生成稳定事实ID；模型只能引用这些ID提出问题和语义建议。每个问题有明确reason与target。完全相同的issueKey在答案仍适用时不得再次询问；不靠模型自报confidence数值决定所有分支。来源缺失等硬问题由规则发起，语义问题由模型建议后经程序验证。

示例稿的“展示查询结果即可”和“打开对应订单详情”只决定用户目标。若答案暗示裁剪录制中的详情步骤，本期不得自动裁剪；最终预览指出目标与已录制步骤的差异，用户在正式编辑能力内处理，或者保留未解决草稿。选择项不是扩大站点授权、创建新操作或免除执行确认的入口。

“暂不确定”是有效的暂缓答案：保留问题并允许生成待完善草稿，不自动选择推荐项，不在后续轮次重复追问同一个问题。普通返回/关闭未提交选项，不算已回答。

## 4. 成功条件如何简化

不要求用户编辑技术条件表单。问题使用自然语言：“怎样才算完成？”；内部区分三个事实：录制观察、用户预期、模型建议。用户说“出现提交成功”仅表示预期，不证明录制实际出现过该文字。

提案调整如下，须随本方案批准后再实施：

- 草稿允许successCriteria为空；缺少条件不导致所有步骤整理失败。
- 工作流保留简短goal和completionMode（automatic/manual/undecided），内部仍是JSON。具体字段命名在实施时与现有契约统一，不建立第二份平行工作流。
- automatic只能使用有明确检查对象与判断方式的条件；Schema合法不代表业务语义已验证。多条条件第一版按全部满足理解。
- 用户明确选择“执行后由我确认”才可为manual，不能用后台默认值掩盖不知道；此模式未来不能自动报告业务成功。
- undecided以及关键步骤/参数仍有歧义时可保存，不能发布。
- 发布为automatic需条件结构合法、关键问题已解决；发布为manual需用户明确选择且关键问题已解决。原有来源、范围、危险动作确认规则不变。重放尚未实现，本期发布不能宣称可执行。
- 现有已发布数据不因新设计被静默改成manual，也不猜测用户目标。重新编辑/发布时按当时当前规则明确处理缺少信息，迁移不删除历史记录。

这一提案替代之前“让用户手动配置复杂成功规则”的待讨论方向，并不移除后台校验。

## 5. 提问页面与关联页面

三张本轮候选只探索同一个提问界面的信息层级：聚焦当前问题、证据优先、带紧凑已答摘要。它们共用以下行为，不是三个技术方案。实际编号以聊天图片显示顺序和DESIGN.md为准。

| 页面/状态  | 正文                                              | 固定操作/返回行为                                     |
| ---------- | ------------------------------------------------- | ----------------------------------------------------- |
| 分析中     | 当前录制名、真实阶段、提供商/模型；不使用伪百分比 | 取消整理；关闭Popup不取消已在途请求                   |
| 等待回答   | 问题、简短原因、关联证据、选项、按需补充说明      | 稍后处理 / 确认并继续；未选时主按钮禁用               |
| 提交中     | 保留当前问题与选择；提交失败显示原页Alert         | 禁止重复提交；不得丢失用户选择                        |
| 稍后处理   | 返回工作流列表，在整理历史入口可找到“待回答”任务  | 不新开窗口、不抢占连接Tab；再次进入原任务继续         |
| 查看已答   | 紧凑问题/答案列表，可明确修改                     | 修改提交后撤销依赖该答案的后续结果                    |
| 继续分析   | 简短当前阶段及已保存答案入口                      | 不重发用户已明确暂缓的问题                            |
| 草稿预览   | 步骤/参数/目标摘要，未解决问题只在相关条目显示    | 保存草稿 / 确认并发布；发布条件不满足时禁用并给出原因 |
| 失败或中断 | 原诊断保留，区分答案保存失败与模型请求失败        | 显式重试；不丢弃已持久化答案，不自动重试              |

“1/2”仅表示当前批次已有两个问题，不代表整个任务还需多少模型轮次。初次进入不默认代选；示意图选中项只是展示选择反馈。模型说明不以HTML执行，引用证据来自本地索引，不能把模型给出的URL当成可直接执行链接。

外框继续使用ExtensionPopup、PopupPage、Box、NavigationBar、ScrollArea；仅正文滚动。短屏优先保留问题与选项，证据可折叠，页脚始终可达。表单使用TanStack Form和现有Field/RadioGroup/Button；标题图标使用title和aria-label。待回答用中性状态，不用错误红色。稍后处理与“暂不确定”不同：前者保留待答状态，后者明确结束该问题的本轮判断。

用户说“弹出问题”在此解释为当前整理页面切换到提问状态；不在网页注入问答、不强制弹出操作系统窗口。Popup已关闭时保留待回答任务，可在扩展图标用非红色“?” badge提醒；是否增加badge作为待决策项，默认仅页面入口提示，避免覆盖录制图标优先级。

## 6. 有界调用与状态机

建议首版：单批最多3问、单会话最多5个不同问题、最多3次模型调用（初次分析加最多两次用户触发的继续）。这些是待确认的产品上限，不是本会话获得的真实测试调用许可。先进行本地受控回归，真实提供商测试另申请次数。

每次“确认并继续”在有剩余本地问题时只保存并换题；最后一题后按钮明确表示会继续整理，才可能调用模型。初次发送授权需涵盖回答文本，不能用过去只覆盖录制的授权静默扩大数据范围。额度耗尽/仍不明确时产出待完善草稿，不重置计数无限循环。

建议会话状态：

```text
analyzing → waiting_input → analyzing → ready → completed
      ↘ failed / interrupted / cancelled
waiting_input → waiting_input（保存答案/稍后处理，不请求模型）
waiting_input → ready（用户结束问答，保留未解决项）
ready → completed（确认保存或发布成功）
```

同一轮中多个问题使用同一问题批次；内部roundId用于区分请求，不另造历史卡片。waiting_input与ready持久化后关闭本次Host、释放内存密钥，不维持心跳或把模型请求挂起等待人类。显式继续时重新创建Host、读取已存凭据、核对配置/授权，发送最小化事实和决策，不重放聊天全文。

首版最多一个未结束整理会话（包括待回答/预览），减少现有单任务体系改动；开始另一录制时给出继续原任务、保存为草稿后开始、取消原任务的选择，不能覆盖原会话。等待只占整理会话名额，不占浏览器页面执行锁，不阻止Bridge或录制。

关闭Popup：已提交数据保留；未提交补充说明不承诺恢复。浏览器/Worker重启：waiting_input和ready按存储恢复，不请求模型；analyzing仍标记interrupted，不能自动补发未知结果请求。预期关闭等待状态Host不应触发HOST_CLOSED失败。取消后迟到结果拒绝。

## 7. 数据与消息契约

建议新增扩展私有OrganizationSession，复用现有工作流数据库增量schema升级，新增会话store；Worker是唯一写入者，不复制全局前端状态。不要在history summary里存整段问题/答案。

| 对象     | 需要保存的信息                                                                                                |
| -------- | ------------------------------------------------------------------------------------------------------------- |
| Session  | id、revision、recordingId、最小事实快照引用/摘要、状态、模型配置快照（无密钥）、轮次/请求计数、结果workflowId |
| Question | id、questionRevision、issueKey、kind、标题/原因、白名单targetRefs、2～4个选项ID及文字、是否允许短说明         |
| Answer   | questionId/revision、answerId、选项ID或deferred、可选短说明、所依据事实/候选内容摘要                          |
| Decision | 明确的语义字段影响、问题/答案来源、适用内容摘要、是否仍适用；不存模型思维链                                   |
| Result   | 当前Workflow JSON、用户目标、完成方式、未解决问题引用，以及独立用户审阅记录                                   |

模型输出使用有界结构：questions或ready，允许同时包含当前语义候选和待澄清项；程序验证ID、选项数量、长度、引用范围和动作不变量。禁止模型直接输出已核对状态、站点授权或执行命令。原始模型响应与完整聊天历史不保存。

拟新增消息（名称待实施前统一）：workflow.organization.get、workflow.organization.answer、workflow.organization.continue、workflow.organization.finish；复用现有start/cancel。answer携带sessionId、expectedRevision、questionRevision、answerId、optionId和可选说明；continue携带已提交revision，不能从Popup直接传完整模型上下文。Host结果携带注册身份、roundId和inputRevision。

先以Worker串行队列和Repository CAS事务落盘，再ACK。相同answerId重送返回原提交结果；相同ID不同正文拒绝；旧questionRevision/旧session revision返回冲突并刷新，不覆盖新答案。提交失败保留表单，不显示“已保存”。模型请求不在持有的数据库事务/串行写锁内等待。

终态工作流创建与session.resultId在同一IndexedDB事务完成；以sessionId唯一关联防止Worker重启生成重复草稿。chrome.storage.local中的任务历史是可修复投影，不宣称跨存储原子性；恢复时按sessionId同步，不从缺失投影重新发起模型请求。仅在投影写入完成后显示历史更新成功，失败可报告“草稿已保存，历史更新失败”。

重试沿用“新增历史记录关联retryOf”，原失败不覆盖；使用当前配置重新确认发送边界，是否复制可复用答案由事实摘要匹配决定，不能跨录制复用。已提交回答的内容绑定用于阻止过期应用，不作为用户确实阅读的证明。

会话记录有界：问题5个、选项每题4个、短说明300字、单会话语义数据不超过现有256KiB输入预算；超限给出明确反馈，不截掉事实假装完整。归档保留遵循现有最多200条终态历史，关联会话在清理时同步处理；活动会话不自动清理，显式取消/保存后才进入保留策略。工作流若保留必要决策依据只保存最小引用/摘要，不依赖可被清理的整个会话才能理解。

## 8. 回答与已有核对机制

答案不是通用“全部已核对”。只有明确问题的答案与实际应用的目标字段/内容摘要一致时，才可作为该项具体歧义已解决的依据。模型进一步改写目标、参数或依赖后，该答案不自动授权改写结果，相关核对重新失效。

不重复询问已经明确解决的同一事项；仍未解决的推断和人工步骤继续沿用步骤详情核对。最终总确认保留“已核对参数、成功条件”，但不再展示复杂条件配置表；答案摘要可查看修改。执行前确认不因整理问答而解除。

第一版修改已答内容时，程序通过targetRefs撤销相关下游决策和草稿核对；不重新清空所有不相关答案。若依赖无法可靠确定，显示将重新整理的范围，用户明确继续才发请求。不要静默推断任意自然语言回答之间的依赖。

## 11. 实施取值与后续边界

- 已批准第2方向的[提问状态v2](../design/browser-extension-recorder/workflow-guided-question-states-v2.png)与[继续/预览v2](../design/browser-extension-recorder/workflow-guided-continuation-states-v2.png)。
- 开工说明采用的上限：单批3问、总计5问、最多3次模型请求，以及一次只保留一个未结束整理会话。
- 已实现“暂不确定→待完善草稿”；人工完成方式由用户显式选择，发布仍受来源及其他问题校验约束。
- 本轮不新增扩展图标提示，沿用整理历史入口。

JSON仍为唯一权威产物。Skill导出只是未来可独立讨论的能力，不纳入本轮开发，也不维护可独立编辑的第二份流程定义。

## 12. 第2方向交互细化（视觉已确认，未实施）

- 相关录制优先展示，不确定性只关联必要步骤，默认最多展示两行。长问题/短窗口可折叠证据，但必须保留步骤范围和可展开入口。点击引用仅查看本地记录，不跳转业务网页或触发动作。
- 初次无选项默认值；选择后才启用继续。处理中禁用重复提交，选择不会立即调用模型。长文允许换行，单选行整行可点击，键盘/读屏保持关联。
- 展开“补充说明”后是当前问题的短文本框，不出现聊天发送按钮；关闭折叠不抹掉当前表单内容。正文滚动，品牌/Tab/导航及页脚固定；360×420不缩小字体来塞下全部内容。
- “稍后处理”已提交答案保留；如果当前题还有未提交选择/文字，复用现有内联放弃确认，允许返回继续编辑或明确放弃本题未提交内容，不默认将它保存为正式答案。失败页没有未提交字段时直接返回列表。关闭浏览器Popup无法保证捕获确认机会，未提交内容仍不承诺持久化。
- 历史“待回答”条目整行进入原任务；历史列表没有“确认并继续”或“稍后处理”页脚按钮。不为待回答改变默认连接Tab，也不添加聊天通知弹窗。
- 模型请求失败时，只对已获存储ACK的答案显示“已保留N项回答”。存储失败不得使用“不会丢失”的文案；使用“回答尚未保存”并留在原问题。模型失败重试仍为新历史记录关联retryOf，不覆盖旧失败；重试前重新核对已保存答案的适用范围。
- 修改已答内容入口位于任务详情/预览的回答摘要，使用当前单题表单回填；应用修改前说明相关后续整理需要更新，未提交取消不失效已保存决策。所有回答和规则必须按session revision复核，不能从UI截图推断已保存。
- 预览显示流程名、目标、步骤、参数与自然语言完成判断；“修改”进入对应引导问题。图中的manual只是示例，不能由自动默认赋予。确认框沿用用户指定“已核对参数、成功条件”，不重复列出已经解决的每个问题。
- 预览“保存草稿”与“确认并发布”均用default实心Button；发布后回列表并刷新，草稿保存后留在编辑页。未解决关键问题时仍能保存草稿，发布禁用并就近说明，不因表单完整就自动授予执行许可。
- 两张v2的审阅通过只覆盖视觉/交互，仍需用户明确实施后才改代码；真实模型调用额度须另行申请。

## 13. 实施落点与边界

2026-10-31在用户明确实施指令后接线。workflow-organization.ts拥有有界问题、内容绑定、决策应用与选择失效；WorkflowRepository拥有version2 additive migration、会话CAS与最终工作流原子落盘；WorkflowService仍为唯一命令/Host协调者。没有建立第二个通用Agent引擎或自由聊天通道。

每次模型响应最多2个澄清问题，预留1个程序生成的完成判断问题；单会话累计最多5问、3个模型请求。信息明确的条件可以直接进入预览，不强制提问。选项含义能确定性应用时直接生成预览；补充说明或修改已被模型使用的答案会要求用户显式继续分析。模型不能提供用户目标、人工完成方式或审批元数据，这些由实际回答应用。超出提问容量标记待完善，不把静默丢弃的问题当作已解决。

答案和后续结果绑定版本，重复提交可返回已提交结果并重新同步历史；前置目标变化会撤销完成判断，修改完成判断不会反向撤销目标。参数/步骤相关决定按目标与依赖失效。明确控件上的意图问题解决后不重复要求语义核对；控件不明确、人工动作与模型新增读取建议仍保留原专项核对。

会话等待时Host被释放；continue核对规范化接口、提供商、模型及版本2发送授权后创建新Host，每轮独立roundId。不能比较对象序列化顺序来判断配置是否改变。旧的未知在途请求在重启后中断，不自动补发；等待中的已提交问题/答案从IndexedDB恢复。

保存草稿原子创建/更新工作流并结束当前会话；未解决问题保留在草稿，详情提供继续完善。在原草稿未被其他编辑改变时可以重新打开原决策会话；已被修改则拒绝覆盖，返回当前冲突提示。最终工作流保存最小决策来源及内容摘要，不保存完整模型正文或密钥。公开草稿仍是唯一JSON产物，未做Skill导出或重放。

预览中的参数是只读摘要，具体参数编辑继续使用保存后的现有编辑页；完成判断提供直接“修改”回到对应引导问题。问题原因不另占常驻小字段，标题悬停与读屏保留说明；键盘/选项/正文滚动与固定页脚按批准风格接入。

真实提供商可能仍产生不合适的问题或建议。本轮仅使用隔离本地服务与合成录制验证状态/数据流程；未经新增额度授权，不验证真实模型质量，不宣称业务重放成功。

实现验证与截图见[应用复核](../../apps/browser-extension/design-qa.md)及[验证矩阵](../poc/executor-validation.md#引导式整理实施验证)。

### 旧路径清理后的当前边界

2026-10-31按用户要求移除无录制编译/Host连接探测模式，workflow.start的recordingId及Host结果roundId为必填。编译只接受已准备的录制证据；独立连接测试仍由model-settings-service调用probeModelConnection，不创建整理历史。Active只保存本轮会话、临时密钥和生命周期身份，不重复保留原始事件/录制对象。WorkflowRepository的草稿创建仅通过updateOrganization完成会话事务，删除旧create入口及单工作流commit中的创建分支。

停用修复字段从当前任务模型移除；读取持久历史仅投影当前白名单字段，未知存储注记不向UI暴露，必要字段格式错误仍拒绝，读取不会删除原记录。中断恢复由recover处理，不再单列旧任务迁入模式。未接入界面的input.remove/step.remove/step.move操作及其专用成功用例撤下，保留未知操作拒绝和来源/依赖约束回归。实际步骤/参数编辑、成功条件校验和会话恢复继续保留。

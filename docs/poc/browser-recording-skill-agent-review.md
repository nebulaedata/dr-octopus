# 录制 Skill Agent 闭环方案审查

> **当前审查边界（2026-10-31）：** 以下 R1–R7 保留旧双引擎方案的审查证据。用户现已确认[统一 ToolLoopAgent 方案](../architecture/browser-skill-unified-agent.md)。R1 的 Core 执行栈恢复问题不再适用，但统一会话恢复仍需验收；R2/R3/R4/R6/R7 的所有权、动作准入、结果、文件快照、上下文约束仍有效；R5 改为 SDK 消息安全投影。新增实测风险是同轮 ask 与自动 execute 动作并存，解决契约为外部副作用工具及整轮准入，尚未接入生产调度。新方案可进入设计，不代表旧风险均已通过运行验收。

> 2026-10-31 · 设计审查，未实施修复、未生成界面、未调用真实模型。审查对象：[闭环方案](../architecture/browser-recording-skill-agent.md)、[ADR-0088](../adr/0088-browser-recording-skill-agent.md)。
>
> 结论：ToolLoopAgent整理、Page Agent Core重放、本地Skill维护的方向可以保留；初次审查有5项P1和2项P2；用户随后取消重放问答及原执行恢复，R1已在设计上通过范围收敛解决，其余4项P1和2项P2继续补齐。它们是提案的未闭合契约，不等于现有产品已经发生这些故障。暂不建议把方案视为已定稿并进入界面设计。

## 审查依据与边界

- 读取当前方案、框架评估、扩展AGENTS和现有Browser协议。
- 核对本地已安装AI SDK 7.0.155的公开声明：工具默认可并发，toolCallConcurrency=1只保证串行执行，不保证模型一轮只返回一次调用。
- 核对Page Agent Core官方v1.12.4源码，与当前PageController版本同线作为候选证据；本项目尚未锁定/安装Core。后续选择其他版本应重新核对，不能把此版本发现机械推到所有版本。
- 本轮没有运行技术小样；源码证明的是边界，不能代替MV3/跨Host/副作用恢复测试。

## R1 · 原P1：两种引擎的“继续会话”能力没有充分区分（设计上已收敛）

**状态更新（2026-10-31）：** 用户明确取消重放onAskUser，单次run只用原生execute；运行前准备输入，Host丢失后结束本次run，不恢复原Core调用。原失效场景不再属于目标能力。需在后续实施验证工具集中无ask_user及不自动重跑，不能把本次设计收敛当成测试通过。

以下保留原审查证据。

**位置：方案§6.2、§7、§12、§14。**

当前设计同时谈同一会话继续、Host释放/重建和Page Agent Core重放。v1.12.4的execute会重新设置任务和history；onAskUser是当前执行中的Promise回调。应用保存了历史，不代表重建后仍有原调用等待答案。

**失败场景：** 用户在重放中被提问，Host丢失。再次execute即开始新Core任务，可能重新执行之前已经完成的操作；旧问题也无法靠恢复UI直接回到已不存在的回调。

**建议：**

- 整理会话：用ToolLoopAgent消息及匹配tool result继续。
- 重放会话：只关闭Popup且Host尚在时，沿用原Core运行；Host被销毁则记录中断，保持应用sessionId但建立新的执行attempt。
- 新attempt先观察当前页面和未知结果，明确剩余目标；不将旧历史当成可直接重复执行的指令。
- 写明Core适配器的公开API与锁定版本，不能依赖修改私有状态来冒充可恢复调用栈。

**验收：** 提交动作之后、结果入会话之前关闭Host；重开会话不得再次提交，原问题/已有结果仍可查看。

## R2 · P1：会话缺少唯一执行所有者与工具执行提交协议

**位置：方案§6.1、§6.2、§8、§14。**

文档有消息版本和幂等回答原则，但未明确谁能认领本次运行、两个Popup同时继续如何处理，以及tool call/预算在哪个事务点提交。

**失败场景：** 两个入口同时读取同一sessionId并创建Host，双倍调用模型/工具；或者工具已经产生效果，结果尚未写入会话时Host丢失，下一次把它当成未执行。

**建议：**

- Session Repository原子认领执行权，返回runId/执行世代；同一会话最多一个有效运行者，旧Host结果不得更新新世代。
- 每次模型请求先记账；每个工具先持久化调用意图并得到ACK，再执行，最后记录结果。
- 明确未派发、已派发未知、结果已提交三种工具状态；继续时按状态处理，不按是否存在结果简单重跑。
- 对模型一轮多个tool call定义整体接纳策略。串行执行配置不能代替“同时只接纳一个待回答调用”规则；特别是submit_skill不得先落盘再发现同轮还有未处理问题。
- 这些都属于会话运行记录和工具调度约束，不增加用户维护的业务流程。

**验收：** 双Popup继续、重复回答、旧Host迟到响应、多工具同轮、请求发出后崩溃和文件回执丢失，均保持预算与副作用正确。

**设计进展（2026-10-31）：** 方案§6.3已补充ToolLoopAgent外部工具结果、单待答调用、同轮多ask/ask+submit拒绝策略及回答原子提交；R2仍待小样验证，没有因SDK具备工具调用能力直接关闭。

## R3 · P1：内建浏览器工具如何经过统一准入还未闭合

**位置：方案§4、§12、§13。**

Page Agent Core v1.12.4的点击、输入、选择等内建工具直接调用pageController；定义了额外BrowserActionTools，不意味着内建动作自动经过现有Worker权限、文档身份和所有权检查。

**失败场景：** 标签页在观察后跳转或权限被撤销；模型按旧元素引用执行内建动作，绕过计划中“每次动作复核”的边界。

**建议：**

- 列出Core内建工具与跨Tab工具的完整适配表，明确观察、点击、输入、选择、滚动、导航/切页分别如何路由和复核。
- 使用公开注入控制器或customTools覆盖/移除机制，证明所有可执行动作均经过同一准入；不复制另一套DOM执行器。
- 严格映射允许的Core配置，禁止将workflow.json对象直接展开成Core配置；脚本执行开关不能由Skill开启。
- 页面观察也要核对允许站点，不能只限制点击而让越界页面内容进入模型。

**验收：** 页面切换、导航、文档替换、权限撤销、伪造运行所有者及Skill未知配置字段均不能越权观察/操作。

## R4 · P1：Core完成信号到业务结果之间缺少具体核对契约

**位置：方案§12。**

当前写了“有观测支持”，但没有定义如何处理Core的完成返回。v1.12.4的done含模型提供的success，执行循环据此形成结果；这不是独立业务验证器的结论。

**失败场景：** 页面只是打开详情，模型宣称完成，产品却展示为“订单已处理成功”；或者返回了另一个订单的结果。

**建议：**

- 区分引擎执行结束、业务结果已核对、结果不充分；不得直接把Core.success映射为产品成功。
- ResultVerifier明确绑定本次Skill快照、参数、Tab/document与最近观测；可确定的匹配由程序验证。
- 自然语言目标不能形式化核对时，展示实际观察到的结果，必要时通过运行会话向用户确认，不回到生成阶段的固定完成方式问卷。
- 输出无法验证时保留不充分状态，不为了结束任务制造成功。

**验收：** 要求提交的任务仍未出现对应结果、结果订单号不匹配、观测来自已切换的页面时，不能仅凭模型done=true报告业务已验证成功；纯读取任务不以页面必须变化为条件。

## R5 · P1：不能将框架原生history直接作为持久会话记录

**位置：方案§6.1、§13。**

Page Agent Core的HistoricalEvent类型包含rawRequest/rawResponse，重试和错误也可携带原始对象。若为了“完整记录思考和工具”直接保存agent.history，会违反方案自身的安全投影要求，可能把页面/业务内容与调试报文一并保存。

**失败场景：** 业务数据从临时模型请求进入长期会话记录；提供商错误对象携带超出预期的诊断内容。

**建议：**

- 明确SessionRecord白名单字段及每种引擎的投影适配器；保留模型实际提供的可展示思考、工具调用/结果与必要usage，不原样序列化native history或Error。
- UI历史与下一次模型上下文都从同一会话派生，但不是同一份字符串直接回灌；提供商必要元数据要单独审核适配。
- 定义数据大小、脱敏、敏感字段处理和保留期限；认证信息不进入记录。
- 思考记录缺失时如实缺失，不拼造或用原始报文填充。

**验收：** 合成认证头、敏感页面字段和提供商错误回显不能出现在会话持久数据及导出中；安全投影后仍能继续有效会话。

## R6 · P2：两文件前后摘要一致，不能证明同一编辑版本

**位置：方案§11。**

前后哈希可以发现读取期间变化，但用户可能先保存新的SKILL.md，几分钟后才更新workflow.json。中间两个文件完全稳定，仍可能语义/参数不一致。因此“避免读到保存一半”表述过强。

**失败场景：** Markdown引用了新参数或新站点，JSON仍旧；部分错误能由引用校验发现，未显式引用的语义冲突不能只靠哈希识别。

**建议：**

- 将保证收窄为读取稳定快照，并做完整跨文件校验；不承诺原子识别任意手工编辑批次。
- 两文件共同形成definitionHash，与本次输入/授权/运行绑定；运行中固定快照。
- JSON采用完整strict schema和显式配置映射，参数作为结构化数据传入，不能把输入值直接拼接成系统指令。
- 若用户要求真正成组提交文件，再另设计编辑完成/版本提交机制；首版不要让用户维护复杂版本清单。

**验收：** 只改一文件、缺参数、畸形JSON、运行中改文件及含特殊文本的参数，行为可解释且不运行错误组合。

## R7 · P2：会话历史与模型上下文的增长策略仍过于笼统

**位置：方案§6.2、§8、§13。**

方案写了字节/事件上限，但未规定长会话如何构造下一轮上下文。完整历史全部回灌可能超限；简单截取最近消息又可能丢失任务边界或产生孤立tool result。

**建议：**

- 会话历史完整保留与模型输入窗口分开；当前指令、录制/Skill快照、未完成调用和关联结果必须保留。
- 大录制/候选用受限引用与按需读取，避免每轮重复整个文件。
- 只处理已闭合的工具轮；不能裁掉pending call而留下回答，也不能删除已确认的用户决策。
- 首版达到上下文上限可明确停止并保留会话，不必立即自建复杂压缩器；如加入摘要，记录来源范围且不把摘要变成新授权。
- 续跑预算不能因为上下文缩短或Host重建而归零。

**验收：** 长录制、多轮校验、长回答及预算耗尽时，保留正确任务边界、配对消息和可解释的继续条件。

## 不应误报为新漏洞的事项

- 用户已经选定ToolLoopAgent整理、Page Agent Core重放；没有依据要求换框架。
- 本机保存依赖Executor、需要Native协议变更，原文已经列为待确认取舍；它们是范围决定，不是本次新发现的实现漏洞。
- 静态校验不能证明业务语义，原文已明确。R4要求补的是运行结果处理契约，而不是给生成阶段重新增加复杂成功条件表单。
- 当前没有Skill Agent新架构的运行代码，本次不能据此宣称线上数据泄漏或重复提交已经发生。

## 建议收束顺序

1. 先补Page Agent Core单次execute的动作准入、历史投影与结果处理（R3/R4/R5）；R1的原执行恢复已从范围中删除。
2. 再补Agent Session执行与工具提交契约（R2）。
3. 明确文件快照与上下文边界（R6/R7）。
4. 以上问题收束后再确认方案并做界面设计。必要的技术小样属于后续需授权的验证，不在本轮偷偷实施。
